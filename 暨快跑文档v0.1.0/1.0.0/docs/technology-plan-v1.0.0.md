# 暨快跑 · 技术选型与快速实现建议

版本：1.0.0｜日期：2026-09-25｜状态：推荐方案，未安装依赖、创建云资源或实施开发。

已知条件：微信小程序优先、后续兼顾 H5；无既有技术偏好，以尽快上线为主；平台免费，不接入交易支付。

## 1. 推荐结论

推荐采用 **普通 uni-app（Vue 3）+ uniCloud + uni-id-pages + uni-admin**，聊天优先验证 **uni-im** 的可裁剪与扩展能力。用户页面按本项目设计开发，底层账号、后台权限、上传和会话等优先复用。前端基础组件优先采用 uni-ui，必要时少量自定义。

uni-app 是跨端应用框架；uniCloud 提供云函数／云对象、数据库及存储等云能力；uni-id、uni-admin 和 uni-im 分别覆盖账号、管理后台与即时通讯基础能力。这些工具不是现成的校园平台，不能直接提供本项目全部业务规则。[uni-app 官方文档](https://uniapp.dcloud.net.cn/)、[uniCloud 官方文档](https://doc.dcloud.net.cn/uniCloud/)、[账号体系](https://doc.dcloud.net.cn/uniCloud/uni-id/summary.html)、[uni-admin](https://doc.dcloud.net.cn/uniCloud/admin)、[uni-im](https://doc.dcloud.net.cn/uniCloud/uni-im)

本次选择普通 uni-app，暂不引入 uni-app x／UTS 作为首版依赖；这是减少团队学习和插件适配验证范围的工程建议，不表示后一方案不可用。实施时按官方兼容性固定一套经过验证的工具和依赖版本，不在本文臆定“最新版本”。

快速起步可优先评估 **uni-starter 普通 Vue 3 模板**，复用登录、个人中心、设置与登录拦截；只保留符合公益项目的入口。若模板裁剪负担较大，则使用普通 Vue 3 空项目导入 uni-id-pages 和 uni-ui。它们提供开发基座，三类校园业务仍按本项目设计实现。[uni-starter 官方文档](https://doc.dcloud.net.cn/uniCloud/uni-starter)

## 2. 三条路线比较

| 路线 | 可复用内容 | 本项目仍需做什么 | 判断 |
|---|---|---|---|
| A：uni-app + uniCloud 生态 | 多端前端、账号、数据库存储、后台基础、聊天 | 信息业务、权限、私聊限制、内容治理及真机适配 | 推荐：符合当前快速上线、无既有技术栈条件 |
| B：uni-app + Java／Spring Boot + RuoYi 系后台 | 前端跨端能力、后台权限与常见管理页面 | 服务部署、数据库运维、小程序用户体系、聊天和业务 | 有 Java 团队或成熟后台时再优先考虑 |
| C：微信原生小程序 + 云端服务 | 小程序原生界面与接口 | 业务、治理；H5 界面后续另建 | 小程序单端深度体验优先时考虑，当前双端目标下复用面较窄 |

对 A“更快”的判断是基于本项目和用户条件的工程推断，不是实测性能或工期承诺。B 不是把 RuoYi 管理页面直接变成面向学生的小程序；C 也不能把原生小程序页面直接作为 H5 使用。框架来源及授权见[研究记录](framework-research-v1.0.0.md)。

## 3. 推荐技术清单

| 部分 | 推荐 | 选择理由与限制 |
|---|---|---|
| 用户端 | uni-app、Vue 3、基础 uni-ui 组件 | 首先构建微信小程序，后续适配 H5；业务卡片和表单自行设计 |
| 开发语言 | Vue 单文件组件 + JavaScript；公共数据结构使用清晰类型注释 | 减少初学者同时适配多种语言的负担；是否全面使用 TypeScript 在样板阶段确定 |
| 状态管理 | 页面状态优先局部管理，登录与会话等共享状态再集中 | 不为所有字段建立全局状态；若所选模板已有状态库，优先沿用 |
| 后端 | uniCloud 云对象／云函数 | 按账号、内容、关系、治理分业务边界，无需首版拆微服务 |
| 数据 | uniCloud 数据库 | 使用其原生数据能力，首版不额外维护独立 MySQL／Redis／Elasticsearch |
| 媒体 | 云存储及可控的访问方式 | 上传、审核、公开、删除分别管理；私聊和待审媒体不能默认永久公开 |
| 登录 | uni-id-pages + uni-id | 复用账号基础与页面，配置微信小程序登录；H5 登录另行适配 |
| 后台 | uni-admin | 复用登录、权限、菜单和管理界面基础；新增内容、举报及复核页面 |
| 聊天 | uni-im，先做验证样板 | 复用会话与消息能力，自定义限额、黑名单和信息卡片；确认微信构建与扩展点 |
| 内容处理 | 提交即进入过滤／待审流程，后台处理疑似内容及复核 | 文本、图片、视频分别设计；不能用文本词库代替媒体审核 |
| 搜索 | 数据库支持的基础关键词与筛选 | 根据实际数据量设计索引，不先引入独立搜索集群 |

工具能力的事实依据参见[研究记录](framework-research-v1.0.0.md)中的官方链接；本表对语言、状态管理、搜索及服务拆分的取舍为本项目建议。

## 4. 能复用到什么程度

| 能力 | 复用基础 | 自定义内容 |
|---|---|---|
| 登录注册 | uni-id 和对应登录界面 | 用户协议展示、业务权限、头像昵称各自七天冷却、多端账号关联 |
| 管理后台 | uni-admin 菜单、权限及界面基础 | 三板块内容列表、媒体预览、举报、复核、下架原因与日志 |
| 会话消息 | uni-im 会话、消息及相关 UI | 回复前一条限额、跨入口按账号对计数、重发去重、黑名单、来源内容可见性 |
| 信息发布 | 表单、上传等基础组件 | 四种表单、信息状态、数量、截止时间、编辑版本与审核规则 |
| 校园墙 | 列表及媒体展示组件 | 点赞、评论、回复、收藏、关注及分享业务、去重和通知 |
| 内容审核 | 可适用的服务接口与后台组件 | 发布状态、异步结果、视频审核、失败处理、人工复核与展示权限 |

不要根据“有登录、聊天和后台”宣称业务已经完成，也不建议为了利用商城模板而保留无用的订单、库存锁定和支付数据模型。

## 5. 服务与数据划分建议

按业务职责划分云端代码，先放在同一项目管理，不创建多个部署系统。

| 业务 | 主要数据 | 关键约束 |
|---|---|---|
| 用户与账号 | 框架账号、业务资料、资料修改时间 | 业务用户与管理员权限分离；渠道标识不直接作为所有业务主键 |
| 发布内容 | 公共内容字段、类型详情、当前版本、审核状态、供需状态 | 审核状态与已完成／已售出等供需状态独立 |
| 媒体 | 所属内容／消息、上传者、处理状态、访问范围、删除状态 | 待审、下架及私聊媒体的权限与页面保持一致 |
| 互动关系 | 点赞、收藏、关注、评论及回复 | 唯一约束和重复请求处理；作者不能单独删除别人评论 |
| 消息 | 复用的会话及消息、账号对的联系权限、来源信息 | 数据结构以 uni-im 当前扩展方式为准，不另造一套不兼容会话 |
| 治理 | 举报、关联版本、处理决定、复核、操作日志 | 修改内容或删除帖子不能抹掉进行中的处理依据 |

以上是逻辑划分，不是确定的数据表定义。框架已有集合不重复创建；先确认字段和扩展约定，再确定 Schema 与索引。

## 6. 三个必须先验证的点

### 6.1 私聊约束能否在服务端落实

uni-im 的通用聊天不等于项目规则已经实现。所有消息发送路径应在服务端检查同一账号对的联系状态、拉黑状态和发送额度；发送请求携带去重标识。两台设备同时发送时也只能有一条申请成功，发送失败重试不能额外占用额度。

先用两个测试账号验证首次申请、第二条拒绝、对方回复解锁、换帖子、撤回、删除会话、拉黑解除、断网重试。如果现成模块无法通过稳定扩展点执行这些检查，应先调整聊天接入方案，再大规模开发页面。

### 6.2 审核不能留下视频缺口

官方 uni-sec-check 文档描述的微信 provider 及相应身份、接口条件需要逐项适配，不能据此宣称 H5、所有媒体或视频已经覆盖。[uni-sec-check 官方文档](https://doc.dcloud.net.cn/uniCloud/uni-sec-check.html)

本项目建议所有媒体提交后先处于非公开状态。文本和图片选择适用的过滤接口，疑似或失败转入明确的待处理状态；视频在自动审核方案落实前采用后台人工审核后公开。人工审核是首版候选方案，须落实审核人员及实际处理能力。若视频处理量超出能力，再核实并接入对应供应商的视频审核／转码服务。没有通过的内容不得默认公开。

### 6.3 公益不等于运行资源免费

uniCloud、存储、流量以及可选短信、审核和视频服务按实际供应商及用量核算，不能把试用额度当作永久免费。具体金额在选择服务空间和供应商时核对官方计费，不在本轮编造月费用。[uniCloud 官方计费](https://doc.dcloud.net.cn/uniCloud/price)

成本控制建议：列表视频封面、点击播放；缩略图；上传大小及发布频率限制；清理无人使用的失败上传；配置预算提醒。限制对用户一致适用，不售卖加量包。平台成本由项目方承担，用户端仍免费。

## 7. 许可证与可迁移性

各组件分别核对许可证。uni-admin 的 MIT 授权不代表同生态全部产品都按 MIT 授权；uni-im 的官方插件协议对运行于 DCloud 产品体系有要求，不能默认将其源码移植到任意服务器或产品。选定的组件版本、协议及必须保留的声明应在实施时记录。[uni-admin](https://doc.dcloud.net.cn/uniCloud/admin)、[uni-im 插件与使用协议](https://ext.dcloud.net.cn/plugin?name=uni-im)

本推荐接受一定云平台绑定，以换取首版开发速度。为了后续迁移，业务内容字段、审核规则和账号映射保持清晰，定期验证数据及媒体备份恢复方式。不承诺未来无成本切换到 Java 或其他云。

## 8. 从选型到上线的顺序

1. **兼容样板**：固定工具及插件版本，完成小程序真机登录、媒体上传、uni-admin 审核，以及两个账号聊天和限额验证。
2. **业务闭环**：按[页面设计](frontend-design-v1.0.0.md)完成三个板块的发布、浏览、详情与作者维护。
3. **完整范围**：完成校园墙视频和六项互动、消息、举报、复核、分享权限及通知。
4. **试运行准备**：落实运行预算、审核负责人、可见性检查、备份恢复和真机验收；平台主体和发布流程另行核实。
5. **后续 H5**：复用适用的 Vue 页面及业务服务，单独验证登录、分享、聊天、媒体和审核能力；不把“可编译为 H5”当作已经完成适配。

暂不给出“几天完整上线”的承诺。样板验证通过后，以实际开发人数、时间投入、后台处理能力和媒体方案排期；这比在尚未验证的插件组合上直接估算全部工期更可靠。

## 9. 本轮待评审结论

本轮建议采用路线 A，并按页面方案实施。尚需在动工前完成的选择是：云空间及预算、登录配置、聊天扩展验证、媒体限制与审核运营安排。无需再次讨论是否抽成或平台支付，既定公益边界继续有效。
